# 重打后候选恢复：线程与状态初查

## 已证实与未证实

用户报告“有时第一次候选顺序不对，再打一遍正常”，尚未提供现场编码、上文和两次候选。不能将以下机制实验当成该现场问题已经复现。

当前本机 `neural_rerank=false`，本机 Qwen HTTP 后端不会参与这次默认菜单重排；引擎 C API 多处以 `g_engine_mutex` 保护共享状态。唯一明确的 detach 线程用于 HTTP 连接失败时唤醒 LaunchAgent，不负责异步写回已产生的候选。尚无证据指向多个线程抢写默认 V5 菜单。

## 固定状态的真实重复测试

在本机数据的隔离副本中，以当前 V5、相同开关、相同词库和学习快照测试：
`jnqu`、`yidm`、`mabc`、`fwjn`、`gojimkyi`、`xmuejmhb`、`puiid`、
`qygfda`、`vgxjuvijxwudi`、`xmzlvgxjuvijxwudi`。

两种上文状态：无上文、固定提交“编辑”；每种 30 轮，每轮包含逐键输入及
一次性 set_input 两种路径，共 1,200 个完整菜单的前 20 项。
同状态重复结果无变化；逐键与一次性路径也无变化。没有提交目标候选，
因此不会把“选词后学习”的合理排序变化误认为重复不稳定。

## 控制实验确认的风险

`mohu_word_order_filter` 与 `mohu_semantic_gate_filter` 除固定扫描数量上界，
还每扫描 8 条检查一次 `os.clock()`，默认超过 2ms 即截断窗口。
这里 `os.clock` 是进程 CPU 时间，原注释称“墙钟时间”并不准确。

相同 20 个候选、相同上文“编辑”、相同评分（第 12 个“目标词”明显高分），
只改变虚拟时钟：慢扫描在 8 条处停止，首选“候选词1”；快扫描收齐 20 条，
首选“目标词”。该差异不需要任何并发线程，也不需要修改词库或学习。

这是已证实的时间相关候选窗口风险，仍未证明用户现场就是此原因。
可能的后续方向是改为确定的数量窗口，保留单键短路和扫描数量上限，
并补做速度、冷启动和真实语境回归；不能直接取消全部上界，避免旧版
补全单字洪流被无界扫描拉干。语义服务启用时还要单独区分启动/超时回退。

证据：`.tmp/candidate-stability/history.tsv`、`fresh.tsv`、`timing.lua`。
本轮仅诊断，没有修改排序规则，也没有覆盖本机运行文件。
